# Upgrade to Endatix 0.9.3

This guide applies to Reporting preview exports that include copied choices, Other text, or checkbox and tag box indicators. Only affected forms need a refresh.

## Before you start

- **Read the release notes of every version you skip.** An upgrade that skips 0.9.2 also needs the [0.9.2 guide](/docs/guides/upgrading/v0-9-2).

## Unanswered checkboxes export empty cells {/* #unanswered-checkboxes-export-empty-cells */}

**What changed (breaking for the Reporting preview):** the indicator columns of an unanswered checkbox or tag box with its own choices no longer write `0` where the respondent may not have seen it. Its columns, Other and None included, are empty:

- in an incomplete submission, which may have ended before the question;
- in a completed submission, when a visibility condition (`visibleIf`) or `visible: false` on the question, or on a panel, dynamic panel or page that holds it, could hide it, or when the form uses its name for two questions.

A question nothing could hide, skipped in a completed submission, still writes `0`. An answered question writes `1` and `0` as before. Copied choices, loops and rankings follow the same rule since 0.9.2. The Crunch codebook is unchanged; Crunch imports an empty cell as No Data. See [Empty Cells](/docs/end-users/submissions/exporting-submissions#empty-cells).

**Who is affected:** forms with checkboxes or tag boxes that can be hidden, or that incomplete submissions leave unanswered, and any analysis that counts those `0`s.

**What to do:**

- Exports read the rows stored when each submission was saved, so existing rows keep their `0`s until they are rewritten. A backfill with `force=true` (`POST forms/{formId}/submissions/backfill`) rewrites them. Without a compile first, an unanswered question in an incomplete submission turns empty, and a completed submission keeps its `0`s.
- To also empty the completed submissions whose question could be hidden, compile the form's schema first (`POST forms/{formId}/reporting/compile-schema`; merge mode is enough, and it records which questions can be hidden), then backfill with `force=true`. For merge plus a forced backfill, use the API as described in [Refresh stored rows](#refresh-stored-rows).

## Copies of copied choices export 0 for shown choices {/* #copies-of-copied-choices */}

**What changed:** a checkbox or tag box that copies its choices from a question that copies its own (for example `pick` copies the selected choices of `aware`, which copies `brands`) now writes `0` for a choice the respondent was shown and did not pick. In 0.9.2 every unpicked choice of such a copy was empty. With the selected mode the copy shows what the source question picked; with all or unselected it shows what the source question was shown, when that can be worked out. See [Empty Cells](/docs/end-users/submissions/exporting-submissions#empty-cells).

**What to do:** restoring the visibility rule from a 0.9.2 schema needs a replace compile. Check the form’s history before choosing replace; see [Refresh stored rows](#refresh-stored-rows).

## Other text with a choice comment box {/* #other-text-with-choice-comment-box */}

**What changed:** a checkbox with Other whose regular choice shows a comment box (**Add a comment box** in the Creator) now exports its Other column as `1` and the typed text in its Other text column. SurveyJS stores the typed text of such a checkbox in its value, and 0.9.2 read it from the question's comment, so it exported `0` and an empty text. Radio button groups and dropdowns with a choice comment box still keep the typed text in the comment, and export as before. A tag box whose choice still has the comment box setting in its JSON (written by hand, or kept from a question converted from a checkbox; the Creator does not offer it on tag box choices) now follows `storeOthersAsComment`, so with it `false` its typed text is exported too. Other tag boxes are unchanged.

**What to do:** compile in merge mode, then backfill; see [Refresh stored rows](#refresh-stored-rows).

## Checkboxes from other form versions export empty cells {/* #checkboxes-from-other-form-versions */}

**What changed:** a checkbox or tag box with its own choices that a submission's form version did not have, because it was added in a later version or removed in an earlier one, now exports empty cells for that submission, Other and None included. In 0.9.2 a completed submission wrote `0` in every one of its columns, as if the respondent had seen it and left it. Submissions saved on a version that has the question are unchanged. See [Empty Cells](/docs/end-users/submissions/exporting-submissions#empty-cells).

**What to do:** no compile, only a backfill; see [Refresh stored rows](#refresh-stored-rows).

## Copies of selected choices export the source's Other {/* #copies-export-the-sources-other */}

**What changed:** a SurveyJS **Choices from question** copy in selected mode, with no **Other** of its own, can offer the source's **Other** when the respondent picks it and enters text. In 0.9.2 a radio button group or dropdown that picked it exported an empty cell, and a checkbox or tag box copy had no **Other** column. Hub **Carry Forward** does not copy the source's **Other**.

The export appends **Other** after the copy's existing categories, using the source question's Other label. A radio button group or dropdown also gains `<question>__other_text` (`<question>--other_text` in csv-shoji) immediately after its answer column. If the copy picked **Other**, the export uses its own non-empty text first. If the copy has no text, it reads the source using the choices and storage settings on the submitted form version. Only if that version is absent or unreadable does it fall back to the latest stored source (`otherFrom`) and catalog. They are not a history of earlier sources.

For a checkbox or tag box copy, `1` means the respondent picked **Other**. An answered copy writes `0` for an unpicked **Other** only when its visibility rule holds and either its form version offered the copy's own **Other** or the source picked **Other** with text. Otherwise the cell is empty. See [Empty cells](/docs/end-users/submissions/exporting-submissions#empty-cells).

**What to do:** merge is enough for a radio button group or dropdown. For checkbox and tag box visibility, use the per-form decision below.

## Refresh stored rows {/* #refresh-stored-rows */}

Check each affected form's current questions and the versions that collected submissions. A compile updates the reporting schema; it does not rewrite stored rows. Choose the compile mode for the form before starting its backfill.

| The form needs | Compile mode | Effect |
| --- | --- | --- |
| Copied **Other** on a radio button group or dropdown | Merge | Adds the category and text column; preserves existing category IDs. |
| Exact visibility for checkbox or tag box copies whose stored rule is missing or changed, including selected copies of **Other** and copies of copied choices | Replace, unless the mixed-history rule below applies | Uses the current visibility rule even for older submissions. Neither mode restores a visibility rule from a version that was never compiled. Merge leaves unpicked indicators empty where it cannot prove a choice was shown. |
| Other text for a checkbox with a choice comment box, or a tag box with that setting and `storeOthersAsComment: false` | Merge | Retains removed choices so historical picks are not reclassified as typed Other text. |
| Empty cells for an unanswered checkbox or tag box that could be hidden | Merge | Records whether the question could be hidden. |
| Empty cells for a checkbox or tag box absent from the submitted version | No compile for this fix alone | Backfill uses the submitted version. |

**Mixed history: default to merge plus a forced backfill via the API.** If a form needs a new visibility rule but has removed questions or choices, reordered choices, or changed what a copy offers, keep the historical answers. An empty unpicked indicator is preferable to a `0` the stored rule cannot support. Replace rebuilds from the current form: it can remove columns, renumber category IDs in current choice order, or reclassify a removed choice as typed Other text. Before making a replace exception, compare before-and-after exports for that form on the same historical submissions. Use replace only after explicitly accepting the specific changes for that form.

1. If a compile is needed, call `POST forms/{formId}/reporting/compile-schema`. Omit `replace` for merge; use `replace=true` for replace.
2. Call `POST forms/{formId}/submissions/backfill` with `force=true` for `completionScope=completed` and again for `completionScope=incomplete`. Page each scope separately: pass each response's `nextAfterSubmissionId` as `afterSubmissionId` on the next request until `hasMore` is false. If the only fix is a checkbox absent from the submitted version, only completed rows change.
3. Check `failedSubmissionIds` on **every** page, including the last. If any IDs are listed, fix the cause and rerun that scope from the start with `force=true`. `hasMore: false` means the scan finished, not that every row succeeded.

In the Hub, **Rebuild reporting data…** with **Full recompile** means replace plus forced backfill. Without **Full recompile**, the Hub merges but skips unchanged submissions. Use the API for merge plus forced backfill.
